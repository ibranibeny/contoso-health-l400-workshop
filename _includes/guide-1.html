Welcome to Contoso Health

Contoso Health is a fictional health insurer whose members check their coverage at hospital front desks around the clock. Its member portal and claims API still run on virtual machines, releases are manual and audits are painful. In this workshop you move it to Azure in Indonesia Central and run it the way an expert platform team would.

Business pain → what you build

  • 1Premium due date, every monthTraffic peaks on the first days of the month. → Autoscale, Azure Managed Redis (B0) in front of PostgreSQL and a per-member rate limit.
  • 2Front desks check eligibility 24/7A hospital can't wait for a slow screen. → Zone-redundant PaaS, health checks and graceful degradation.
  • 3Claims arrive in burstsRetries must never create duplicate claims. → An idempotent claims API backed by PostgreSQL.
  • 4Manual releases, painful auditsEvery change should be reviewed, traceable and repeatable. → IaC, GitHub rulesets, OIDC, attestations and agentic workflows.

The Well-Architected Framework in ten minutes

The Azure Well-Architected Framework (WAF) is Microsoft's guidance for designing and running a workload on Azure: "a collection of application resources, custom code, AI models, data, and supporting infrastructure". S207 It is organised in five pillars. Each pillar comes with design principles, a design review checklist, trade-offs, design patterns and a maturity model. S201 Every decision in this workshop is tagged with the pillar it serves.

Two different "WAF"s in this workshop

Well-Architected Framework: design guidance with five pillars; the pillar tags REL, SEC, COST, OPS and PERF and the "WAF scorecards" refer to it. Web Application Firewall: the layer-7 firewall on Application Gateway (the WAF_v2 SKU, the WAF policy, DRS 2.2); it gets its own primer below and Module 4.

Hub-and-spoke networking in ten minutes

A hub-and-spoke topology puts the network services that every workload shares into one hub virtual network, and gives each workload its own spoke, peered to the hub. S213 The hub holds shared infrastructure only (firewall, gateways, Bastion and DNS), and workload teams own their spokes. S214 S46 This is the network your landing zone (Module 2) designs and your IaC (Module 3) deploys.

Six rules that matter at L400

1
Peering is non-transitiveTwo spokes peered to the same hub can't reach each other through it. Spoke-to-spoke traffic goes through the hub firewall with user-defined routes, or through Virtual Network Manager connectivity. S213 S214
2
Ingress stays in the spokeApplication Gateway is a workload component: deploy it in the workload's spoke, not as a shared service in the hub. S46
3
Egress is explicit and inspectedNew VNets have no default outbound access. Production routes 0.0.0.0/0 to the hub firewall; the lab attaches a NAT gateway. S197 S199
4
One gateway for every spokeGateway transit shares the hub's VPN or ExpressRoute gateway: "Allow gateway transit" on the hub side, "Use remote gateways" on the spoke side. The Basic VPN SKU doesn't support it. S214 S216
5
DNS is a platform servicePrivate DNS zones are central and linked to every VNet. A DNS Private Resolver in the hub connects on-premises DNS, and at scale policy writes the private endpoint records. S47 S214
6
Check the limits before you size a hubThe limits page allows 650 peerings per VNet, while the networking design guide still says 500. The Virtual Network Manager hub-and-spoke configuration supports up to 1,000 spokes. S217 S214

Hub-and-spoke or Virtual WAN?

Customer-managed hub-and-spoke

  • Full control of routing and of the hub's services
  • Fewer than about 30 branch VPN connections
  • The choice in this workshop S45 S214

Azure Virtual WAN

  • Microsoft-managed hubs with automatic routing and global transit
  • 30 or more branches, many regions, or VPN-to-ExpressRoute transit S45 S214

Web Application Firewall on Application Gateway in ten minutes

The Web Application Firewall (WAF) on Application Gateway inspects every HTTP request at the edge of the spoke, before it reaches the portal or the API, and blocks common attacks such as SQL injection and cross-site scripting. S218 It is configured as a WAF policy on the WAF_v2 SKU: custom rules, managed rule sets, a mode and request-size settings. S219 Application Gateway V1 retired on 28 April 2026, so WAF_v2 is the only choice. S234

What happens to a request

1
Custom rulesYour rules, in priority order (1–100, up to 100 per policy): allow, block or log on IP address, country, method, URI, headers or body, plus rate limits per client IP. S223 S224
2
Managed rule setsDRS 2.2 (OWASP CRS 3.3.4 plus Microsoft Threat Intelligence rules) scores every request; Bot Manager 1.1 classifies bots as bad, good or unknown. S221 S222
3
DecisionIn Prevention mode a block is HTTP 403 "The request is blocked." and the connection is closed; in Detection mode the match is only logged. S218 S225
4
EvidenceEvery decision goes to AGWFirewallLogs (Blocked, Allowed, Matched or Detected) and to the WAF metrics. S231 S233 S232

What the Contoso Health policy contains

SettingIn the kit (Bicep and Terraform)

Two rate limits work together. The WAF limits claim submissions per client IP at the edge; the API limits each member to five claims a minute and answers 429. A broken integration is stopped before it costs the API anything, and a single member cannot flood the claims queue from many addresses. S224

Six things an L400 engineer should know

!
Most specific policy winsA policy can sit on the gateway, a listener or a path rule; the most specific one applies. S219
!
Exclusions, not DetectionFix a false positive with a per-rule exclusion on the exact field; selectors have no regex. S227
!
Bot metric blind spot"WAF Bot Protection Matches" only counts Bot Manager 0.1. For 1.x, query the log. S232
!
Spelling trapThe ARM property is spelled negationConditon (no second "i"), while Learn's custom-rule example writes negationCondition. Bicep needs the API spelling. S236 S223
!
Previews stay outJavaScript challenge and the HTTP DDoS rule set are preview on Application Gateway; the kit does not use them. S230 S229
!
No AGC hereApplication Gateway for Containers is not offered in Indonesia Central, and its WAF supports only DRS 2.1. S235

Indonesia Central: three zones, no pair

The residency policy leaves one region, indonesiacentral. It has three availability zones and is listed among the nonpaired regions S01 S02: "Many of the newer regions provide multiple availability zones ... and don't have a region pair." S02 Consequences:

  • In-region HA means zones. There is no platform-managed failover to a partner region.
  • No geo-redundant backup for PostgreSQL in this region S17, so infra/bicep/modules/data/postgres.bicep sets geoRedundantBackup: 'Disabled'.
  • Cross-region DR must be designed and approved. A copy in Southeast Asia is not automatic and collides with the residency policy: a decision for Rudi (recovery targets) and Nadia (residency), not a Terraform flag.

Reliability: write the DR decision down before you build

The kit implements in-region resilience only: zones plus backups that stay in the region. Surviving a regional outage needs either an approved residency exception for a secondary region (replication, DNS failover, a second set of private endpoints) or an explicit acceptance of the regional risk with a documented recovery time. Both are legitimate; an unwritten assumption is not. Record it as your first ADR.

The application: four tiers, five functions

  • Web (app/web): a React 19 single-page app in TypeScript, compiled by Vite into dist/, served by a small Node.js backend-for-frontend (BFF), app/web/server.js, that also forwards /api/*. React is compiled in at build time, so the BFF has no runtime npm dependencies and no deployed package carries node_modules.
  • API (app/api): framework-free Node.js ES modules with four runtime dependencies (pg, redis, @redis/entraid, @azure/identity) and an optional @azure/monitor-opentelemetry.
  • PostgreSQL: the system of record. Redis: cache, idempotency fast path and rate-limit counters, never the only copy of anything.

The portal's five pages (My coverage, Find care, My claims, Claims desk, System) exercise these endpoints. Why a BFF? The browser talks to one origin only. The web server forwards /api/* to API_BASE_URL, drops hop-by-hop headers, propagates x-request-id, maps an upstream timeout to 504 and an unreachable API to 502, sends a strict Content-Security-Policy (script-src 'self'; style-src 'self': inline scripts and styles in the markup are refused) and adds HSTS only behind TLS. In Azure the API therefore needs no public endpoint and no CORS policy. The BFF also owns the cache policy of the build:

// Vite fingerprints everything under /assets (index-3f9c2a.js), so those files never change and can
// be cached for a year. index.html names the current bundles, so it is always revalidated. [PERF]
export function cacheControl(rel) {
  if (rel === '/index.html') return 'no-cache';
  if (rel.startsWith('/assets/')) return 'public, max-age=31536000, immutable';
  return 'public, max-age=3600';
}

Revalidating index.html costs a 304 (Last-Modified), so a release shows on the next page load while the bundles never travel twice. Paths without a file extension fall back to index.html, and /web/info reports the build version from APP_VERSION or dist/version.json, which the pipeline stamps with the commit.

The UI shows the platform at work. Every call goes through apiFetch (app/web/src/lib/api.ts), which returns the body plus what the platform added. Chips under each result show the status, the round trip, cache HIT, MISS or BYPASS (x-cache), the API and web instances that answered (x-served-by, x-web-instance), idempotent replay and the request ID. A 429 starts a countdown from Retry-After; a 403 that is not JSON, the Application Gateway block page, appears as error code blocked; the footer names the instances, platform, region, storage and cache that served you.

Decision: React SPA behind a backend-for-frontend, not Azure Static Web Apps

Context
After the build the portal is static files plus calls to /api. Azure Static Web Apps suits static front ends where server-side rendering isn't required, served from globally distributed points S241. The API, however, is reachable only through its private endpoint.
Options
(a) Static Web Apps for the files; the browser then needs its own route to the API. (b) Files on the web tier, the API published separately with CORS. (c) Files and an /api proxy in one small Node.js BFF on the existing web tier.
Choice
(c). The reasons are the kit's design choice, not a Learn statement: the API stays private, the browser sees one origin (no CORS), both tiers sit behind the same Application Gateway WAF, and the same BFF runs on App Service (zip) and AKS (image).
Consequences
You operate and scale a web tier instead of a managed static host, and every release needs a build (CI builds once and ships dist/; Module 3 does it by hand). In return the BFF owns the security headers and cache policy, adds no runtime dependency, and its /readyz lets App Service Health check and Kubernetes readiness drop a web instance that has lost its path to the API.

Both packages need Node.js 24+ (Vite itself needs 20.19+ or 22.12+ S243). Node 24 is Maintenance LTS until 30 April 2028, Node 26 the Active LTS S180; App Service recommends Node 24 LTS S11, pinned as NODE|24-lts. The portal's packages are pinned to the versions the kit was built and tested with (app/web/package.json); newer majors exist S247, so upgrades arrive as Dependabot pull requests with CI as the gate.

// Cache-aside: read the cache, fall back to PostgreSQL, populate the cache.
async function cached(ctx, key, ttl, loader) {
  const t0 = performance.now();
  const raw = await cache.get(key);
  ctx.timing('cache', performance.now() - t0);
  if (raw) {
    ctx.cacheStatus = 'HIT';
    return JSON.parse(raw);
  }
  const t1 = performance.now();
  const value = await loader();
  ctx.timing('db', performance.now() - t1);
  ctx.cacheStatus = cache.isBypassed?.() || raw === undefined ? 'BYPASS' : 'MISS';
  if (value !== null && value !== undefined) await cache.set(key, JSON.stringify(value), ttl);
  return value;
}
  • HIT: found in Redis; PostgreSQL untouched.
  • MISS: Redis answered "not found"; the value came from PostgreSQL and was stored with its TTL.
  • BYPASS: the cache did not answer (or its circuit is open); the value came from PostgreSQL and nothing was stored.

app/api/src/http/server.js emits this as x-cache plus server-timing: cache;dur=…, db;dur=…, total;dur=…. TTLs live in app/api/src/config.js and are overridable (for example CACHE_TTL_ELIGIBILITY_SECONDS). New claims and decisions delete the member's keys; changes the API never sees, such as a premium payment posted by finance, are bounded only by the TTL, so up to 60 seconds of "not covered" after paying is a trade-off Rudi must accept. The ch:v1: prefix versions the JSON shape: bump it when the shape changes.

Performance Efficiency: size for the BYPASS case

The provider list is one shared key, so every 300 seconds concurrent misses reach PostgreSQL together; at higher scale add request coalescing or a jittered TTL. Above all, size PostgreSQL for a cache outage on premium day, when every lookup becomes a query.

The first failure opens a 15-second circuit during which Redis is not called, so a dead cache adds no latency; app/api/src/cache/redis.js adds disableOfflineQueue: true (fail fast, never queue) and reconnect back-off capped at 5 seconds. While Redis is down, reads are BYPASS, the idempotency fast path is skipped (the database still deduplicates), /readyz stays 200 with "cache":"degraded", and the rate limit fails open. Availability over strict throttling is a conscious choice: write it into the runbook.

PoC item: Redis down when the API starts

app/api/src/index.js replaces a failed Redis client with a stub that always throws, so that instance serves BYPASS until it restarts; the stub never reconnects. Whether client.connect() fails fast or keeps retrying with this reconnect strategy depends on the redis client, and the kit does not test it. Start the API with Redis stopped, record what happens, and add it to the runbook.

Shallow liveness, deep readiness

router.get('/healthz', async () => ({ body: { status: 'ok' } }));

// Readiness: can this instance do useful work right now?
router.get('/readyz', async () => {
  if (state.shuttingDown) return { status: 503, body: { status: 'shutting-down' } };
  const [db, redis] = await Promise.all([
    repo.ping().then(() => 'ok').catch((e) => `error: ${e.code || e.message}`),
    cache.ping().then((ok) => (ok ? 'ok' : 'degraded')).catch(() => 'degraded'),
  ]);
  // PostgreSQL is required; the cache is optional (the API degrades to the database).
const ready = db === 'ok';
  return { status: ready ? 200 : 503, body: { status: ready ? 'ready' : 'not-ready', checks: { postgres: db, cache: redis } } };
});

This is the Health Endpoint Monitoring pattern: shallow liveness, deep readiness for required dependencies only, optional dependencies excluded, and App Service Health check pointed at the readiness endpoint S198. App Service's guidance agrees that the path should return a 5xx when a critical dependency is down S10.

EndpointChecksWho calls it
/healthz (API, web)Nothing: is the process alive?Application Gateway probe (web app), Kubernetes liveness and startup probes, Docker HEALTHCHECK
/readyz (API)PostgreSQL required, Redis reported only, 503 while shutting downApp Service Health check, Kubernetes readiness
/readyz (web)The API's /healthz within 2 sApp Service Health check, Kubernetes readiness

The web tier checks the API's liveness, so a database outage stops at the tier that owns the connection. The gateway probe stays shallow because a deep probe would mark every backend unhealthy during a database outage and stop even the requests the cache and the portal's static files can still serve.

App Service Health check pings every minute (200 to 299 is healthy), removes an instance from the load balancer after 10 failed pings (WEBSITE_HEALTHCHECK_MAXPINGFAILURES, 2 to 10), replaces one unhealthy for an hour (at most one per hour, three per day per plan), needs two or more instances and does not follow 302 S10. The caveat: when a shared dependency fails, every instance is unhealthy, so App Service keeps them all in the load balancer, yet replacement still occurs S10. A replacement cannot even start until PostgreSQL returns, because migrations run at start-up.

Deep dive: one identity, three username rules

PostgreSQL maps the identity to a role named after it, created from its object ID by pgaadauth_create_principal_with_oid S24; hence PGUSER=id-ch-api-lab. Redis takes the object ID as username S28. App Insights needs only the role assignment S183. So a PGUSER that differs from the role name breaks PostgreSQL logins, while an identity recreated under the same name (new object ID) breaks Redis and the PostgreSQL role mapping made from the old ID.
