Two rate limits, two keys

Decision: two rate limits, per client IP at the WAF and per member in the API

Context

Options
(a) The API limit only. (b) A WAF limit only, grouped by client address, geolocation or nothing, with X-Forwarded-For variants S224. (c) Both, keyed differently.

Troubleshooting

Symptom: in Prevention, attack rows fail with an "app" status such as 200 app

Cause: the policy is still in Detection after step 5, or was changed outside IaC; if the baseline rows fail with 403 too, the URL bypasses the gateway. Fix: check the mode (step 1), redeploy the lab parameters, test http://<AGW_IP>.

Symptom: the burst button or the browser test's 429 check gets 403

Cause: everyone using one gateway from one venue shares a client IP and 60 claim POSTs a minute. Fix: raise wafClaimsRateLimitPerMinute or waf_claims_rate_limit_per_minute for the lab, redeploy, and pass the new value to WAF_RATE_LIMIT_PER_MINUTE.

Symptom: AGWFirewallLogs returns no rows

Cause: the logs have not arrived yet, LAW_ID is not the customerId of log-ch-idc, or you query AzureDiagnostics, which the kit's Dedicated setting does not use S231. Fix: wait, recompute LAW_ID, query AGWFirewallLogs.

Symptom: the exclusion deployed, but the note is still blocked

Cause: another rule matched too; a Terraform excluded_rule_set without type and version targets OWASP 3.2 S237; or the JSON-field PoC fails. Fix: exclude every RuleId of the transaction, set the rule set explicitly, and revert if the excluded RuleId still matches.

Symptom: the rate-limit row says 0 blocked

Cause: WAF_RATE_LIMIT_PER_MINUTE is below the deployed threshold, the policy is in Detection S223, or the client cannot exceed the threshold within the window. Fix: pass the deployed value, check the mode, and note the timing in the PoC.

From code deployment to containers: what changes and what must not

On the Jakarta VMs and on App Service (Module 3) the unit of deployment is a folder started by the host's own Node.js runtime (on App Service: the API with its node_modules, the portal as server.js plus the compiled dist/). In a container it is an image: runtime, OS userland, dependencies and code, frozen together and addressed by a digest. Three responsibilities move to you: the base OS and its patch cadence, the user the process runs as, and how the process starts and stops.

What must not change is the contract between the application and its host. The kit's app was written as a twelve-factor app, so this module is packaging, not refactoring:

PropertyWhere the kit already does it
Configuration only from environment variablesapp/api/src/config.js reads every setting from process.env; the same image runs on a laptop, App Service and AKS.
JSON logs on stdoutapp/api/src/logger.js and app/web/server.js; App Service and Container insights collect stdout, so no agent or log file in the image.
Graceful shutdown on SIGTERMapp/api/src/index.js stops accepting work, drains requests, closes the PostgreSQL pool and Redis client, force-exits after SHUTDOWN_TIMEOUT_MS (default 20 s).
Shallow liveness, deep readinessapp/api/src/routes/index.js: /healthz checks only the process; /readyz requires PostgreSQL, reports Redis without failing on it, and returns 503 while shutting down.
No local stateState lives in PostgreSQL and Redis; migrations take an advisory lock so replicas can start together (app/api/src/db/migrate.js).
Identity without secretsapp/api/src/azure/credential.js: workload identity on AKS, the user-assigned managed identity on App Service, your own sign-in on a laptop.

Each health endpoint has deliberate consumers. The Health Endpoint Monitoring pattern recommends a shallow liveness check, a deep readiness check limited to required dependencies, and pointing App Service Health check at the readiness endpoint S198; App Service expects that path to return a 5xx when a critical dependency is down S10. So App Service Health check calls /readyz (PostgreSQL required, Redis optional because the API degrades to the database), while the Application Gateway probe and the Kubernetes liveness probe stay on /healthz: a database outage must never restart healthy processes. The caveat is shared fate. When PostgreSQL fails, every instance is unhealthy at once; App Service then stops removing instances from the load balancer but still replaces instances S10 (at most one per hour and three per day per plan S10), which cannot fix a database. Module 6 shows how Kubernetes readiness reacts to the same outage.

The credential code also follows Learn's advice to use a specific credential in production instead of DefaultAzureCredential S182; only a laptop falls through to the chain:

Deep dive: PID 1, signals and the shutdown budget

The kernel does not apply a signal's default action to PID 1 of a PID namespace, so a SIGTERM that PID 1 does not handle is ignored until the runtime sends SIGKILL. Both kit servers register SIGTERM and SIGINT handlers, so exec form needs no init process (docker run --init matters only when a process spawns children to reap). With shell form or npm start a wrapper becomes PID 1 and signal delivery depends on it — measure it with lab step 4.

In AKS the budget is terminationGracePeriodSeconds: 30: the preStop hook sleeps 5 s so endpoints stop routing first, then the API drains and force-exits after SHUTDOWN_TIMEOUT_MS (20 s). 5 + 20 < 30, so SIGKILL never cuts a claim submission in half. Change one number and re-check the sum.

Reliability: tests inside the image build, and what they cost

Because the checks run in the build stage, no web image can exist for a commit that fails the type check or a unit test, wherever it is built: a laptop, Compose or the Container build workflow. The price: every cold build installs the whole toolchain (Playwright included, which only the browser tests use); a failing test surfaces as a failed docker build; and on a pull request CI runs the same checks three times, in app-unit, in container-build and in the e2e job's Compose build. Only the unit tests in src/ run in the image: the build stage copies src/ but not test/ (the BFF tests) or e2e/, which app/web/.dockerignore also excludes, so those stay in CI (Module 9). The kit pays the extra minutes for images that carry their own proof.

Base image and Node.js line

Decision: base image for the Node.js 24 images

Context
Both images need Node.js 24 on linux/amd64, the AKS node architecture. Nadia wants minimal surface and a support statement; Bayu wants builds that survive a slow or rate-limiting public registry. MCR publishes Azure Linux images such as base/nodejs:24 and distroless/nodejs:24-nonroot, but states that "Azure Linux container images are supported only for internal Microsoft use" S121.
Options
(A) Official node:24-slim from Docker Hub. (B) Azure Linux distroless from MCR: no shell, non-root, smallest, but outside its support statement S121. (C) A, imported into your own ACR with az acr import and referenced by digest.
Choice
A as the Dockerfile default so the kit builds anywhere; C in CI and production by setting NODE_BASE_IMAGE to <acr>.azurecr.io/<repo>@sha256:<digest>. B is rejected for its support statement, not its design.
Consequences
Slim still ships a shell, package metadata and npm; non-root, root-owned code and the Kubernetes security context compensate. With a digest pin you own the patch cadence (re-import, PR, rebuild). Because the kit avoids shell-dependent tooling (node -e health check, native sleep in preStop), a supported distroless base later is a one-line change.

Decision: Node.js 24 (Maintenance LTS), not Node.js 26 (Active LTS)

Context
Node.js 26 is Active LTS. Node.js 24 entered Maintenance LTS on 20 October 2026 and reaches end of life on 30 April 2028; 22 ends on 30 April 2027; 20 has been end of life since 30 April 2026 S180. The App Service Linux quickstart recommends Node 24 LTS S11 (NODE:24-lts S12) and offers 26 as well.
Options
24 on both hosting paths; 26 on both now; 26 in containers and 24 on App Service.
Choice
24 everywhere: NODE|24-lts, node:24-slim, node-version: 24 in CI, the Node 24 dev-container feature and "node": ">=24" in engines. .github/dependabot.yml ignores Node.js majors in the docker ecosystem, so a major upgrade is always a deliberate PR.
Consequences
One runtime and one code path to test. Maintenance releases focus on critical and security fixes S180, so plan the move to 26 well before April 2028: NODE_IMAGE default, linuxFxVersion in both IaC flavours, CI and dev container, then the full test suite.

Break it on purpose: a read-only root filesystem without /tmp

Variant: delete USER node, rebuild, and id prints uid=0(root). Pod Security Admission will not catch it in Module 6, because PSA judges the pod spec, which still says runAsNonRoot: true and runAsUser: 1000 — the pod is admitted and runs as 1000. Symptom: Compose never starts web: "dependency failed to start … api is unhealthy"

Cause: the API's HEALTHCHECK never passes, usually because the process exited at startup (PostgreSQL not ready, a migration error). Fix: read the JSON error in docker compose logs api, fix it, run docker compose up -d again.

Egress: outbound type and private subnets

AKS supports six outbound types: loadBalancer (default), managedNATGateway, userAssignedNATGateway, userDefinedRouting, and none and block for network-isolated clusters only (block is preview) S199. The kit lets the spoke own egress: lab uses userAssignedNATGateway, prod userDefinedRouting with 0.0.0.0/0 to the hub firewall. userAssignedNATGateway requires the NAT gateway to be associated with the node subnet before the cluster is created S199, so "workload stack before aks stack" is a prerequisite, not a convention.

The subnets are private on purpose. New VNets created with a Microsoft.Network API version released after 31 March 2026 get private subnets by default, but older API versions leave default outbound access implicitly on S197. The kit pins 2024-05-01, so it sets defaultOutboundAccess: false explicitly on snet-aks-nodes and snet-aks-ilb (and on the private-endpoint and ops subnets); the delegated snet-aks-apiserver stays at the default, because private subnets don't apply to delegated subnets that host PaaS services S197. A node subnet without the NAT gateway or the route therefore has no internet egress at all — which is the point.

Identity and access

Cluster admins (parameter clusterAdminPrincipalIds, from CLUSTER_ADMIN_OBJECT_ID) get Azure Kubernetes Service RBAC Cluster Admin plus Cluster User Role. The GitHub deploy identity gets AcrPush, Cluster User Role and RBAC Writer scoped to <cluster id>/namespaces/contoso-health — it can roll out workloads but cannot create the namespace, which is why scripts/aks-postprovision.sh does that once as an admin. The control-plane identity id-ch-aks-<env> is user-assigned and created first, so it already holds Network Contributor on the spoke VNet when AKS validates the subnets; the internal load balancer needs that role too S112. The AKS-managed kubelet identity gets AcrPull.

Workload identity: one identity, two hosting platforms

The aks stack adds federated identity credentials to the existing id-ch-api-<env> and id-ch-web-<env>, so the PostgreSQL role, Redis access policy and Key Vault role that App Service uses already cover the pods. Deep dive: where the token goes

app/api/src/azure/credential.js sees AZURE_FEDERATED_TOKEN_FILE and builds a WorkloadIdentityCredential. For PostgreSQL, node-postgres accepts a function as the password S181, so every new physical connection calls getToken for https://ossrdbms-aad.database.windows.net/.default with the identity name as role S23; @azure/identity caches and renews the token. For Redis, @redis/entraid requests https://redis.azure.com/.default, uses the object ID as user name and re-authenticates open connections when it refreshes at 80% of the lifetime S28 S29. Nothing is written to a Kubernetes Secret, and a leaked pod spec contains only a client ID.

Ingress: why Application Gateway and an internal load balancer

Decision: AKS ingress path in Indonesia Central

Context
The community ingress-nginx project ended best-effort maintenance in March 2026 S109. Microsoft supports the NGINX-based application routing add-on "for critical security patches … through November 2026" and points to the application routing Gateway API implementation (GA), Application Gateway for Containers or the Istio add-on's Gateway API S110 S111. Application Gateway for Containers is not available in Indonesia Central S37. Application Gateway WAF_v2 already sits in the spoke for App Service.
Options
(1) NGINX, managed or community: retiring. (2) Application Gateway for Containers: not in the region. (3) WAF_v2 → internal load balancer with a static private IP → web Service. (4) WAF_v2 → internal application routing Gateway API (approuting-istio) → HTTPRoutes, as in the AKS baseline S63. (5) The Istio add-on's Gateway API: a full mesh for one route.
Choice
(3) by default, (4) as the documented evolution (k8s/optional/gateway-api/, enableGatewayApi / enable_gateway_api).
Consequences
Option 3 uses only documented Service annotations: azure-load-balancer-internal, azure-load-balancer-internal-subnet and azure-load-balancer-ipv4, which replaces the deprecated loadBalancerIP S112.           volumeMounts: [{ name: tmp, mountPath: /tmp }]
      volumes: [{ name: tmp, emptyDir: { sizeLimit: 64Mi } }]
  • Security context. runAsUser: 1000 is required, not decorative: USER node is non-numeric, and the kubelet cannot verify a non-numeric user against runAsNonRoot. readOnlyRootFilesystem goes beyond the restricted profile; the /tmp emptyDir (64Mi) is the only writable path. The web pods (k8s/base/web.yaml) carry the same context with a 16Mi /tmp: the BFF only reads the React build in dist/ and logs to stdout, so a read-only root filesystem costs it nothing.
  • Probes. Startup allows 60 s (2 s × 30) for first-start migrations. Liveness is the shallow /healthz and never checks dependencies; readiness is the deep /readyz (PostgreSQL required, Redis optional), as the Health Endpoint Monitoring pattern recommends S198.
  • Shutdown. The native preStop sleep (no shell needed) lets endpoints drain before SIGTERM; 5 s + the 20 s app timeout fit in the 30 s grace period.
  • Placement. Zone and hostname spread with maxSkew: 1; ScheduleAnyway prefers availability over strict balance when a zone is short of capacity.
  • Capacity. CPU requests drive the HPA (70% target, min 3, max 12 in base, scale-down stabilization 300 s against flapping after the monthly premium-day peak); memory limits but no CPU limits, to avoid throttling. PDB maxUnavailable: 1; rolling update maxUnavailable: 0.

Network policies (enforced by Cilium) start from default-deny for ingress and egress, allow DNS to kube-dns, then open exactly what the app needs:

  podSelector: { matchLabels: { app.kubernetes.io/name: api } }
  policyTypes: [Ingress, Egress]
  ingress:
    - from: [{ podSelector: { matchLabels: { app.kubernetes.io/name: web } } }]

Port 10000 alone is enough because the kit's Managed Redis uses the EnterpriseCluster policy; with OSSCluster clients also connect to shards on 85XX ports S30 and this policy would break. The 443 rule (Entra ID, Application Insights) is broad; in prod the hub firewall narrows it by FQDN. The overlays differ in a few patches: lab runs 2 replicas with seed data and the operations API on; prod runs 3+ replicas, PGUSER id-ch-api-prod, ILB IP 10.120.3.70 and private-endpoint CIDR 10.120.2.0/24.

Deep dive: PostgreSQL down — App Service versus AKS

Liveness is shallow on both platforms, so no process restarts. Readiness is where they differ. On App Service, Health check on the API's /readyz marks every instance unhealthy, and because all of them are, App Service keeps them in the load balancer while still replacing instances S10: the React portal still loads, and its API calls show errors except for cached answers. On AKS, readiness is fail-closed: all API pods turn NotReady, the api Service has no endpoints, the web pods' /readyz (which calls the API) fails, the web Service loses its endpoints and Application Gateway's :8080 probe fails — members get a 502 for the whole portal. That is correct for API calls and harsh for the portal's static files, which the BFF could still serve. The pattern says to exclude optional dependencies from readiness S198; whether the API is optional for the web tier is a product decision worth an ADR of your own.

Reliability: three zones, every layer

Both node pools span zones 1–3, pods spread by zone, PDBs limit voluntary disruption to one replica, rollouts never drop below desired capacity, and the API server SLA is 99.95% with zones on Standard S85. The data tier needs the same care: PostgreSQL zone-redundant HA in prod S25 and Managed Redis zone redundancy by default S31 (Module 3).

Security: nothing to steal in the namespace

No local accounts, no Kubernetes Secret, no imagePullSecrets, no public API in prod, restricted Pod Security, default-deny network policies, and a deploy identity confined to one namespace. A leaked manifest contains client IDs and host names only.

Decision: required status checks are opt-in

Context
.github/workflows/ci.yml runs only for app/** and .github/workflows/iac-validate.yml (Bicep, PSRule, Terraform, kubeconform v0.8.0, actionlint 1.7.12) only for infra/**, k8s/**, workflows and ps-rule.yaml. A workflow skipped by a path filter reports no check at all, so a required check from it stays "Expected" forever and blocks, for example, an infra-only PR waiting for app-unit (api) (comment in scripts/github/apply-governance.sh).
Options
(1) No required checks: reviewers see CI but nothing forces green. (2) Require only checks that run on every PR. (3) Drop the workflow-level path filters and filter inside the workflow, so every required check always reports. (4) One always-running aggregator job as the only required check.
Choice
(1) by default, (2) through REQUIRED_CHECKS (comma-separated job names such as app-unit (api),app-unit (web), added with strict_required_status_checks_policy: true). Move to (3) or (4) when the team is ready to own the workflow change.
Consequences
Until then a red PR can be merged by an approver, so the approval gate and the PR template's evidence table carry the weight. Strict mode forces branches to be up to date before merging, which costs CI minutes. Check names include the matrix suffix; a typo is another "Expected" forever. Verify how skipped jobs report in your repository before you rely on (3).

Environments: lab, prod, copilot

Environments gate jobs: up to six required reviewers, optional prevention of self-review, wait timers up to 43,200 minutes and branch or tag policies; environment secrets are released only after the rules pass. On private repositories on Free, Pro or Team, required reviewers and wait timers exist only for public repositories, so private repositories need GitHub Enterprise S129. The script creates lab and copilot without protection, and prod with required reviewers from PROD_REVIEWERS (self-review prevented unless SOLO_WORKSHOP) and a deployment branch policy that allows the default branch only. If the reviewers call fails, it retries without them and warns. copilot holds the client ID of a read-only identity (Reader and Monitoring Reader) for the Copilot cloud agent (Module 8).

OpenID Connect to Azure, in depth

A job with permissions: id-token: write can request a signed JWT from GitHub for the audience api://AzureADTokenExchange S135. azure/login@v3 presents it to Entra ID with only a client ID, tenant ID and subscription ID — all repository or environment variables. Entra ID compares issuer (https://token.actions.githubusercontent.com), subject and audience with the federated credentials on the user-assigned managed identity id-ch-github-<env> and, on an exact match, returns an access token. A managed identity has no secret that could leak, expire or need rotation; the trust is the subject string.

The subject depends on the trigger S136: repo:ORG/REPO:environment:NAME for a job that references an environment, …:ref:refs/heads/main for a branch, …:pull_request for a PR, and the environment wins over pull_request. Repositories created after 15 July 2026 use the immutable form repo:OWNER@OWNER_ID/REPO@REPO_ID:…; older repositories keep the old form unless they opt in through an organisation or repository setting or the REST field use_immutable_subject, and a rename or transfer after that date switches them too S136 S137. Names can be reused by someone else; numeric IDs cannot, which is the point. The bootstrap script picks the format like this:

created_ymd="${CREATED_AT:0:10}"
created_ymd="${created_ymd//-/}"
format="${OIDC_SUBJECT_FORMAT:-}"
if [ -z "${format}" ]; then
if [ "${created_ymd}" -ge "${IMMUTABLE_SINCE}" ] || [ "${opted_in}" = "true" ]; then
    format="immutable"
  else
    format="legacy"
fi
fi
case "${format}" in
  immutable) SUBJECT_PREFIX="repo:${OWNER}@${OWNER_ID}/${REPO}@${REPO_ID}" ;;
  legacy) SUBJECT_PREFIX="repo:${OWNER}/${REPO}" ;;
  *) die "OIDC_SUBJECT_FORMAT must be immutable or legacy" ;;
esac

The heuristic reads the creation date and the opt-in flag from the API. It cannot see a rename or transfer after the cutover, and it warns when a custom subject template (use_default: false) is in use; in those cases trust the OIDC debug workflow and override with OIDC_SUBJECT_FORMAT (the credential "create" is a PUT, so re-running updates subjects in place). For older repositories Learn's migration order is: add the new credential, enable immutable subjects, validate, remove the old one S138.

Each identity holds at most 20 federated credentials and none may contain wildcards; flexible federated identity credentials are in preview and not yet in the CLI or Terraform S139, so the kit stays on exact subjects S95. The script creates …:environment:<env> and, for lab only, …:pull_request for the IaC validate plan job. Its comment states the trade-off: a PR runs the workflow from its own branch, so anyone with write access can use the lab identity from a PR — acceptable for a lab subscription, never for prod. Fork PRs never receive OIDC tokens (comment in .github/workflows/iac-validate.yml).

Deep dive: why a feature branch cannot borrow the prod identity

Three locks must all open. The prod client ID is an environment variable, visible only to jobs that reference prod. The prod environment allows deployments from the default branch only and, where your plan allows, waits for its reviewers. And Entra ID accepts only the exact subject …:environment:prod: a job that drops the environment gets …:ref:refs/heads/<branch> or …:pull_request, which match no prod credential. The pull_request credential exists on the lab identity alone, and the lab identity's roles end at the lab trust boundary you chose for it.

Least privilege for the pipeline identity

The stacks create role assignments — AcrPull for the kubelet, Network Contributor for the AKS identity, Key Vault Secrets User for the API — so the pipeline must be able to write role assignments. That is exactly the permission an attacker wants. The bootstrap script uses Learn's constrain-delegation pattern, cited by title in its comment ("Delegate Azure role assignment management using conditions"): Contributor plus Role Based Access Control Administrator with an ABAC condition that limits which roles it may assign or remove:

  CONDITION="((!(ActionMatches{'Microsoft.Authorization/roleAssignments/write'})) OR (@Request[Microsoft.Authorization/roleAssignments:RoleDefinitionId] ForAnyOfAnyValues:GuidEquals {${allowed}})) AND ((!(ActionMatches{'Microsoft.Authorization/roleAssignments/delete'})) OR (@Resource[Microsoft.Authorization/roleAssignments:RoleDefinitionId] ForAnyOfAnyValues:GuidEquals {${allowed}}))"

${allowed} holds the eight roles the IaC assigns: AcrPull, AcrPush, Key Vault Secrets User, Monitoring Metrics Publisher, Network Contributor, Website Contributor, AKS RBAC Writer and AKS Cluster User Role. A write is allowed only if the requested role is in the list; a delete only if the existing assignment's role is. prod adds Azure Deployment Stack Owner, needed for denyWriteAndDelete deny settings S67; copilot gets Reader and Monitoring Reader only; PLATFORM_DEPLOY=true adds Resource Policy Contributor for the platform stack. Re-runs compare conditions and delete an assignment whose condition differs, so an unconstrained RBAC administrator is never left behind.

Decision: permissions of the GitHub deploy identity

Context
Deployment stacks and Terraform create resources and role assignments across rg-ch-<env>-idc, rg-ch-aks-<env>-idc and the hub; the identity runs code from every merged PR.
Options
(1) Owner. (2) Contributor + User Access Administrator. (3) Contributor + RBAC Administrator constrained to the IaC's roles. (4) Contributor only, with a human applying every role assignment.
Choice
(3), at subscription scope, per environment identity.
Consequences
A compromised pipeline cannot grant Owner, Contributor, User Access Administrator or AKS RBAC Cluster Admin to anyone, itself included, so cluster-admin assignments stay a human task: .github/workflows/infra-deploy.yml deliberately does not pass CLUSTER_ADMIN_OBJECT_ID. Do not mix owners of the aks stack — if you deployed it by hand with cluster admins, a pipeline run would try to remove assignments it may not delete. Residual risk: the condition constrains roles, not principals or scopes (the pipeline could still hand AcrPush to another principal), and Contributor at subscription scope is broad; narrowing both is a PoC item for your landing zone.
