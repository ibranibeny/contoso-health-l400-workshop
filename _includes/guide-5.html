How to use this runbook

  • Order. Platform, workload, database bootstrap, application; AKS adds its stack, post-provisioning, images and manifests. Stacks find each other by fixed names (infra/bicep/README.md).
  • Paths. A (App Service) is the minimum; B (AKS) builds on A1 to A4; C repeats both from GitHub Actions. Deployment tests describes each test once.
  • Flavour. Tabs mark where Bicep and Terraform differ; the choice applies page-wide. Keep one flavour per environment, as their name suffixes differ (infra/terraform/README.md).
  • Where. The repository root, in a codespace (Module 9) or a shell with the tools below; keep it open, as later steps reuse its variables. Commands target lab.
  • Status. App tested locally on 27 Nov 2026; the IaC was reviewed statically but not yet compiled: the "IaC validate" workflow builds it on your first push. The authors have not yet run it end to end in Azure, so every "Expected" is the designed result: your first deployment is the real test.

Deep dive: three different "healthy" answers

The gateway probes liveness (/healthz). Through the gateway, /readyz is the web tier's readiness: does the API answer (app/web/server.js)? The API's readiness (PostgreSQL required, Redis optional) is what App Service Health check polls, failing on a critical dependency as recommended S10 S198; only the VNet reaches it. A green gateway can hide an unready API: T4 proves the whole path.

T4 Smoke test

Checks /healthz, /readyz, /api/info; eligibility for CH-100001 twice (x-cache MISS, then HIT); providers; and one claim sent twice with one Idempotency-Key (201, then 200 with idempotent-replay). SMOKE_WRITE=false skips claims; SMOKE_DATA=false skips everything needing demo data, which prod lacks; SMOKE_WAIT_SECONDS waits for /healthz; SMOKE_MEMBER_ID, SMOKE_PROVIDER_ID and SMOKE_TIMEOUT override defaults.

scripts/smoke-test.sh "http://${AGW_IP}:8080" # AKS listener
SMOKE_WRITE=false SMOKE_DATA=false scripts/smoke-test.sh "http://<prod-gateway-ip>" # prod

Expected: a result table, PASSED: all checks passed against <url> and exit code 0, with SKIP rows for switched-off checks; failures print hints and exit 1.

T5 WAF test

Harmless look-alike attacks, recording who answered. A 403 counts as the WAF's only with the Application Gateway Server header or a non-JSON body (the app answers JSON). T9 Rollback

Rehearse it. App Service: redeploy a previous folder from A5.

Reading a failed test

Symptom: the version never goes live

Cause: another build is still served: a failed deployment, a restarting web app, an unhealthy backend, or APP_BASE_URL pointing elsewhere. Fix: read the deploy output, call /web/info, check backend health (T3), redeploy the web zip.

Symptom: /readyz answers 503 after the first deployment

Cause: the API started before the database bootstrap; its migrations could not log in, so it never became ready and the web tier reports checks.api not ok. Fix: scripts/db-bootstrap.sh lab, then az webapp restart --resource-group "$RG" --name "$API_APP" (AKS: kubectl rollout restart deployment/api -n contoso-health); rerun with SMOKE_WAIT_SECONDS. Until then App Service keeps the unhealthy instances in rotation but still starts replacing them S10.

Symptom: x-cache: BYPASS

Cause: the API cannot use Redis: the REDIS_* settings, the private endpoint or its DNS (T2), or the access policy for id-ch-api-lab; an instance started during a Redis outage may bypass until restarted (a PoC item in Module 1). Fix: check "cache" in the API's readiness (T3), repair, restart the API. A first lookup showing HIT is a warm 60-second cache: wait, or set SMOKE_MEMBER_ID.

Symptom: the WAF test shows "200 app" for an attack

Cause: Detection mode (a new policy's default S220; the kit sets Prevention through wafMode / waf_mode), or a URL without the gateway: docker compose, a codespace port, the internal load balancer. Fix: check az resource show --resource-group "$RG" --name waf-ch-lab-idc --resource-type Microsoft.Network/ApplicationGatewayWebApplicationFirewallPolicies --query properties.policySettings.mode -o tsv and the URL. Attack rows failing with 403 gateway instead mean WAF_MODE says Detection while the policy blocks.

Symptom: a browser test fails only through the gateway

Cause: usually a WAF false positive. Fix: open the screenshot (e2e-artifacts/<test>.png, or the run's e2e-artifacts-* artifact), find the Blocked row in AGWFirewallLogs (T8), and add a narrow per-rule exclusion in the IaC S227; never switch to Detection to get green. In prod, BlockOpsApiFromInternet blocks by design (wafBlockOpsApi).

Symptom: 429 during the tests

Cause: the API allows five claims per member per fixed minute; smoke, browser and manual claims for CH-100001 add up. Fix: wait for Retry-After, about a minute. A gateway 403 on POST /api/claims is the WAF rate limit instead (after the rate-limit test, or many users behind one NAT): wait, or raise wafClaimsRateLimitPerMinute in lab.

Platform failures (quota, OIDC, skipped jobs, held Key Vault names): see Appendix B.
