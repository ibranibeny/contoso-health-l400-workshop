Context

Azure landing zones in one page

An Azure landing zone consists of a platform landing zone (usually one per tenant: the management group hierarchy plus shared connectivity, identity, management and security services) and workload landing zones. Workload teams own their workload landing zones; the platform team owns governance S38 S42. Newer Learn pages say "workload landing zones" where older ones said "application landing zones" S38; the kit's contract still uses the older term.

The design rests on eight design areas (Azure billing and Microsoft Entra tenant; identity and access management; resource organization; network topology and connectivity; security; management; governance; platform automation and DevOps) S39 and five design principles (subscription democratization; policy-driven governance; single control and management plane; application-centric service model; alignment with Azure-native design and roadmaps) S40.

The management group hierarchy starts at an intermediate root named after the organisation. Under it: Platform (Security, Management, Connectivity, Identity), Landing zones (Corp, Online, Local), Sandboxes and Decommissioned. The Security management group was added in 2025 for SIEM and Sentinel tooling S41 S38. Mind the naming drift: newer pages call Corp "Internal ('Corp')". Pick one name in your IaC and alias the other in your documentation, or your policy assignments will not match the diagram.

Subscription vending is the platform mechanism that issues workload subscriptions programmatically. Azure Verified Modules provide it as br/public:avm/ptn/lz/sub-vending (Bicep) and Azure/avm-ptn-alz-sub-vending/azure (Terraform) S42. The recommended way to build the platform itself is the "Platform landing zone accelerator with Azure Verified Modules (AVMs) for Terraform or Bicep". The classic options are on their way out: classic ALZ-Bicep Retiring is deprecated and its repository will be archived on 16 February 2027, and the caf-enterprise-scale Terraform module Retiring was archived on 15 September 2026 S43 S44.

Deep dive: why "one zone per service" matters

From inside a linked VNet, every PaaS name resolves through a privatelink.* CNAME to an address in snet-private-endpoints (verification step 3 in infra/bicep/README.md). From anywhere else the same name resolves to the public endpoint, which refuses connections because public access is disabled. Per-spoke copies of a zone cause split-brain DNS, the classic "works in one VNet, not in the other" failure (comment in private-dns-zones.bicep). Hence one zone per service for the organisation, links per VNet, and registrationEnabled: false so VMs never pollute privatelink zones. Module 3 deletes a link on purpose.

Context

Egress: nothing leaves without a decision

Default outbound access, the implicit internet egress of VMs without an explicit method, is being phased out. Existing VNets keep it. Subnets in new VNets created with a Microsoft.Network API version released after 31 March 2026 are private by default (defaultOutboundAccess=false); the earlier 30 September 2025 date was superseded. Older API versions, and Terraform providers pinned to them, leave the property unset, which means implicitly allowed. Private subnets "aren't applicable to delegated or managed subnets used for hosting PaaS services" S197.

The kit pins Microsoft.Network API 2024-05-01, older than that cut-over, so it cannot rely on the new default. It sets defaultOutboundAccess: false explicitly on snet-private-endpoints, snet-ops, snet-aks-ilb and snet-aks-nodes, and leaves snet-appgw, snet-app-integration and snet-aks-apiserver at the default: the last two are delegated subnets, and the App Gateway subnet is the open question below S197. Where traffic must leave, egress is explicit: in lab a NAT gateway ng-ch-lab-idc with a static public IP on snet-app-integration, snet-ops and snet-aks-nodes; in prod a route table sending 0.0.0.0/0 to the hub firewall, with BGP route propagation disabled.

PoC item: Application Gateway v2 in a private subnet

Learn makes no statement either way about App Gateway v2 in a subnet with default outbound access disabled, so the kit leaves snet-appgw at the default (its gateway egresses through its own public IP, and the kit's comment notes that a 0.0.0.0/0 UDR is not supported there). Learn does say that private-frontend-only gateways cannot reach the internet without a NAT gateway or NVA S200. Verify in your lab: deploy with snet-appgw private, then check backend health and Key Vault certificate retrieval. Repeat the test when you move to a Microsoft.Network API version newer than the cut-over, because the default flips S197.

Decision: NAT gateway in lab, Azure Firewall with UDRs in prod

Context
CAF recommends NAT Gateway as the default outbound method S48; the AKS baseline sends egress through Azure Firewall S63. Premium v4 App Service lacks stable outbound IP addresses S03, but with route-all VNet integration S08 its internet egress uses whatever the subnet uses.
Options
(a) NAT gateway per spoke. (b) Hub Azure Firewall Standard with an FQDN allow-list and a 0.0.0.0/0 route on the egress subnets.
Choice

Consequences
Lab gets a stable, allow-listable egress IP without hourly firewall cost, but no inspection; the kit's comment also notes that a Standard NAT gateway is zonal, not zone-redundant. Prod gets default-deny with logs in the AZFWApplicationRule and AZFWNetworkRule tables, at the price of an always-on firewall and an allow-list to maintain. Security: preventive beats detective

A Deny is evaluated on the create or update request, so the resource never exists; an Audit or AuditIfNotExists finding appears only after the next compliance evaluation (about 30 minutes according to infra/bicep/README.md), when the risk already exists. The aks stack writes a Network Contributor assignment on the spoke VNet and federated credentials on the workload identities into rg-ch-<env>-idc. Globally unique names add a suffix, take(uniqueString(subscription().id, 'ch', env), 6) in Bicep and substr(sha1("<subscription>-ch-<env>"), 0, 6) in Terraform, so the two flavours produce different kv-, app-, psql- and redis- names: deploy one flavour per environment.

Decision: wire stacks by deterministic names, not by outputs or remote state

Context
Three stacks, two IaC flavours, separate owners, and pipeline identities that should hold the least privilege possible.
Options
(a) Pass outputs, as stack outputs into parameters or terraform_remote_state. (b) Look resources up by naming convention. (c) Publish values to a shared configuration store.
Choice
(b), documented in infra/terraform/README.md section 4.
Consequences
No identity needs to read another team's state, plans stay independent, and either flavour can consume the platform the other one built, because the looked-up names carry no suffix. In return, names become an API: renaming one is a breaking change. A lookup fails at preview time if the producing stack is missing, which at least makes the order explicit. The coupling is invisible to tooling, so grep for a name before you change it.

Watch out: same address, different index

The AKS ingress IP 10.110.3.70 is computed as cidrHost(cidrSubnet(addressPrefix, 27, 26), 5) in infra/bicep/workload/main.bicep but as cidrhost(…, 6) in infra/terraform/workload/locals.tf: Bicep's index starts at the first usable host, Terraform's at the network address. Port address maths between the flavours by checking the result, never by copying the index.

Operational Excellence: names are your interface contract

The output names are identical across flavours (webAppName, postgresFqdn, appGatewayPublicIp, …), so scripts and workflows work with either tool, and the workflows choose the flavour with IAC_TOOL. Treat the naming rules in infra/bicep/README.md as a versioned contract: review changes to them like changes to a public API.

Deep dive: what what-if cannot see

What-if is a diff against the control plane, not a dry run. It is noisy, it reports resources that exist but are not in the template as Ignore, it cannot resolve reference(), and nested templates it cannot evaluate stay invisible S68. It does not prove that a SKU has capacity, that a role assignment has propagated or that the resource provider accepts two operations at once. Read it as "what will Azure Resource Manager try?", not as "will it succeed?". The kit previews with az deployment group what-if; Learn now also documents what-if for deployment stacks S67, which is worth a PoC.

Deployment stacks (GA) manage a set of resources as one unit S67. actionOnUnmanage decides what happens to resources that leave the template: deleteAll, deleteResources or detachAll. Deny settings (none, denyDelete, denyWriteAndDelete) protect the managed resources on the control plane only, with up to five excluded principals. Managing deny settings requires the Azure Deployment Stack Owner role; Azure Deployment Stack Contributor is not enough S67.

The lab uses none on purpose: the break-it exercises need write access, most participants do not hold Azure Deployment Stack Owner, and deny settings stop no data-plane access anyway. In prod they turn "only the pipeline changes infrastructure" from a promise into an enforced rule. In CI, Learn's recommended GitHub Action is azure/bicep-deploy v2, which supports stacks and what-if S73; the kit's workflow calls az stack directly.

Azure Verified Modules are Microsoft's standard for IaC modules (resource, pattern and utility modules), published as br/public:avm/res/… for Bicep and Azure/avm-res-… for Terraform S65; the platform landing zone accelerator and subscription vending are built on them S42 S43. Bootstrapping PostgreSQL without a password

After the workload deploys, the server exists but the application cannot log in yet. IaC cannot finish the job for four reasons:

  • Password authentication is disabled, and the only way in is the private endpoint, from inside the spoke.
  • The Entra administrator is the managed identity id-ch-dbadmin-<env>, set through the ARM administrators child resource (Learn still lists SDK and CLI management of Entra administrators as "coming soon") S24.
  • The API's role must be created inside PostgreSQL with pgaadauth_create_principal_with_oid(roleName, objectId, objectType, isAdmin, isMfa) S24.
  • The database contoso_health is deliberately not created by IaC, so that the admin owns it and can grant on it.

scripts/db-bootstrap.sh therefore runs on vm-ch-ops-<env> through az vm run-command invoke. The VM has no public IP and no inbound port; the command travels over the Azure control plane. The VM's identity is the Entra admin, so the script asks the instance metadata service for a token and uses it as the password:

# Entra token for the dbadmin identity from IMDS; audience = Azure Database for PostgreSQL.
imds="http://169.254.169.254/metadata/identity/oauth2/token?api-version=2018-02-01&resource=https%3A%2F%2Fossrdbms-aad.database.windows.net&client_id=${ADMIN_CLIENT_ID}"
…
# For Entra authentication the access token is the password (valid about one hour).
export PGPASSWORD="${token}"
…
  sql "SELECT * FROM pgaadauth_create_principal_with_oid('${API_NAME}', '${API_OID}', 'service', false, false);"
…
  sql "CREATE DATABASE ${DB}"
…
sql "GRANT CONNECT, CREATE, TEMPORARY ON DATABASE ${DB} TO \"${API_NAME}\""
echo "DB_BOOTSTRAP_OK"

The API role (named after id-ch-api-<env>, mapped by object ID, so display-name changes cannot break it) receives only CONNECT, CREATE and TEMPORARY on one database: no server-level rights, no azure_pg_admin, no CREATEROLE or CREATEDB. CREATE lets the API create and own its schema app through its own migrations (Module 1). The script validates every value it interpolates into SQL (GUID and FQDN patterns), never prints the token, is idempotent, and looks for the DB_BOOTSTRAP_OK marker, because run-command reports success even when the script fails.

Security: separate the admin from the application

Two identities, two privilege levels. id-ch-dbadmin can administer the server but is attached only to a VM without inbound access, driven by people with Virtual Machine Contributor (or Contributor) rights. id-ch-api can do exactly what its migrations need in one database. Compromising the API does not yield the admin, and no human ever holds a database password. Audit who may run commands on vm-ch-ops-<env>: that right is your database admin right.

Shipping the code by hand, for now

Zip deploy takes a package as-is by default S239; only with build automation would Oryx run npm install and npm run build on the server S240. The kit keeps that off (SCM_DO_BUILD_DURING_DEPLOYMENT=false on both apps), so App Service builds nothing and you build before you zip. The API zip contains its production node_modules from npm ci --omit=dev. The web zip contains exactly what the deploy workflow ships: server.js, package.json and the compiled React app in dist/, with no sources and no node_modules; the start command stays node server.js. Check your understanding

  1. Why do the stacks look each other up by name instead of reading outputs or remote state?
    Answer

    No pipeline identity needs read access to another team's state, plans stay independent, and either flavour can consume the platform. The price: names are a breaking-change surface, and lookups fail when the producer is missing.

  2. Why can't IaC create the API's database role, and why does the bootstrap run on a VM through run-command?
    Answer

    The role is created inside PostgreSQL with pgaadauth_create_principal_with_oid S24, over a connection that is possible only through the private endpoint, authenticated as the Entra admin. The ops VM carries the admin identity and sits in the spoke; run-command reaches it over the control plane, without inbound ports or SSH.

  3. The Bicep validation failed before creating anything, but the Terraform apply created some resources first. Why?
    Answer

    ARM's preflight evaluates Deny policies for the template's resources before deploying. Terraform's plan never consults Azure Policy, and its apply sends one request per resource, so non-denied resources succeed and stay in state.

  4. What does denyWriteAndDelete protect, and what not?
    Answer

    Control-plane writes and deletes on the stack's managed resources, for every principal except up to five excluded ones S67. It does not protect data-plane access (reading Key Vault secrets or database rows) or resources outside the stack.

  5. App Service Health check, the gateway probe and the smoke test are all green, yet members see Not found. How, and which test would have caught it?
    Answer

    The web zip shipped without dist/. server.js answers /healthz and /readyz itself and proxies the API paths the smoke test calls, so none of them needs the build. The browser tests (and the WAF test's baseline GET /) load the page and fail.

How the policy decides

This module goes one level below the Web Application Firewall primer. A WAF policy is a resource of its own, associated with the whole gateway, a listener (per site) or a path rule (per URI); the most specific association wins, and every association needs WAF_v2 S219. The kit associates waf-ch-<env>-idc with the gateway, so the :80 listener (App Service) and the :8080 listener (AKS, Module 6) share it (infra/bicep/README.md).

Custom rules run before the managed rule sets S218. A custom Allow or Block ends the evaluation; Log writes an entry and lets the remaining custom and managed rules run S223. Then DRS 2.2 scores the request and Bot Manager 1.1 classifies the client S221 S222; this guide claims no order between the two. The HTTP DDoS rule set Preview would run before everything else S229; the kit does not use it.

Prevention blocks and logs: HTTP 403, connection closed. Detection only logs S218, even for custom Block rules S223. A new policy starts in Detection S220; the kit sets Prevention through wafMode or waf_mode. The response is the default 403 "The request is blocked." S225: other status codes are possible S225, but the Terraform resource has no argument for them S237, so both flavours keep it.

Watch out: Allow and redirects skip your rules

Allow skips every remaining custom and managed rule S223: an Allow for a partner hospital's addresses would exempt all its traffic from DRS, so the kit has none. Gateway-level redirects bypass custom rules S223; with a TLS certificate, the kit's :80 listener only redirects to :443 (infra/bicep/modules/network/app-gateway.bicep), and the HTTPS request that follows is evaluated normally.

Managed rules: anomaly scores and bots

DRS 2.2 is OWASP CRS 3.3.4 plus Microsoft Threat Intelligence rules, at paranoia level 1 with its level-2 rules disabled. Its 18 rule groups, such as SQLI, XSS and MS-ThreatIntel-SQLI, are what exclusions refer to S221.

Matches add up to an anomaly score: Critical 5, Error 4, Warning 3, Notice 2. At 5 or more the request is blocked in Prevention and logged in Detection S221. One Critical match is enough, one Warning is not, a Warning plus a Notice is. Every matching rule logs a Matched row; the verdict is a separate Blocked or Detected row S221.

Bot Manager 1.1 blocks malicious bots, allows verified search engine crawlers, blocks unknown search engine crawlers and logs unknown bots by default S222 S218. It runs beside DRS, not instead of it: Terraform requires exactly one OWASP or Microsoft_DefaultRuleSet set S237.

Exclusions and log scrubbing

Fix a misfiring rule with an exclusion, not with Detection or by disabling the rule. Per-rule exclusions (CRS 3.2 and later, Bot Manager 1.0 and later) are preferred over global ones. They match a header, cookie or argument (form field, JSON entity or query string argument) by key, name or value; Learn recommends values over names, which remain for backward compatibility. Operators are Equals, StartsWith, EndsWith, Contains and EqualsAny; selectors have no regex, XML bodies are not supported, and JSON selectors are case-sensitive S227.

In ARM an exclusion scopes itself through exclusionManagedRuleSets, ruleGroups and rules, and an empty rules list excludes the whole group S236. In Terraform, excluded_rule_set defaults to OWASP 3.2 S237, a rule set the kit does not run: set Microsoft_DefaultRuleSet 2.2 explicitly, and carry exclusions over at every DRS upgrade S221.

Scrubbing keeps matched data out of the log. Its fields include RequestArgNames, RequestPostArgNames and RequestJSONArgNames S228. The kit masks the JSON key note; the selector is case-sensitive, and scrubbing needs a matching Content-Type, which the API guarantees by accepting only application/json (infra/bicep/README.md).
